أنت مطور Flutter Web خبير في بناء واجهات حكومية حديثة، وتعمل على مشروع نسك Nosok، وهو نظام شبه مستقل لإدارة خدمات الحج والعمرة والرحلات الدينية، ويجب تطوير واجهاته وفق نظام الواجهات السيادي الخاص بمنصة PalWakf:

PWF-SIS — PalWakf Sovereign Interface System

المطلوب تنفيذ دفعة تطوير كبيرة ومتكاملة بعنوان:

Mega Batch Nosok UI —
Public Service Portal + Internal Operations Console
+ PWF-SIS Compliance
+ Responsive Anti-Overload UX
+ Role-Based UI Separation
+ PalWakf Integration Readiness

==================================================
1. الهدف العام
==================================================

تطوير واجهات استخدام نظام نسك بحيث يصبح جاهزًا بصريًا وتشغيليًا للاندماج مع منصة PalWakf، مع الحفاظ على كونه نظامًا شبه مستقل وظيفيًا.

يجب أن يحتوي نسك على واجهتين واضحتين:

1. واجهة المواطن / الجمهور:
   Nosok Public Service Portal

2. واجهة الموظف / الإدارة:
   Nosok Internal Operations Console

نفس النظام ونفس البيانات الخلفية، لكن واجهتان مختلفتان حسب نوع المستخدم والدور والصلاحيات.

القاعدة الحاكمة:

شاشة المواطن = رحلة خدمة Service Journey
شاشة الموظف = مساحة تشغيل Operational Workflow
والبيانات وسير العمل مشتركة خلفيًا

==================================================
2. الالتزام بـ PWF-SIS
==================================================

يجب أن تلتزم كل واجهات نسك بنظام PWF-SIS.

PWF-SIS يعني:

1. هوية بصرية موحدة مع PalWakf.
2. ألوان منضبطة:
   - الأزرق السيادي.
   - الذهبي الوقفي.
   - الأحمر الملكي #B22222.
   - الأخضر للنجاح.
   - البنفسجي/الرمادي للمحتوى المقيد.
3. RTL كامل.
4. دعم Dark Mode.
5. دعم Visual Identity Admin / Published Overrides.
6. Contrast Governance:
   - لا نص فاتح فوق خلفية فاتحة.
   - لا نص ضعيف فوق Hero أو صور.
   - أي تدرج أو صورة تحتاج طبقة قراءة Scrim.
7. Runtime States موحدة.
8. Anti-Overload UX.
9. Responsive حقيقي حتى الموبايل.
10. لا تصميم خاص منفصل لنسك خارج هوية PalWakf.

ممنوع:
- اختراع ألوان جديدة خارج PWF-SIS.
- إنشاء شكل مستقل لكل صفحة.
- تصميم أزرار أو جداول أو بطاقات خارج النظام.
- الاعتماد على شاشة desktop فقط.
- عرض أخطاء backend خام للمستخدم.
- استخدام legacy.dart في الملفات الجديدة.

استخدم flutter_riverpod.dart في الملفات الجديدة.

Nosok owns:
- بيانات الحج والعمرة.
- الطلبات.
- الحملات.
- المجموعات.
- المرفقات.
- المراسلات.
- المتابعة.
- Workflow الخاص بالخدمة.

PalWakf/PWF-SIS owns:
- الهوية البصرية.
- Shell.
- Runtime States.
- البطاقات.
- الجداول.
- النماذج.
- التباين.
- Responsive.
- Anti-overload.
- قواعد الصلاحيات البصرية.

==================================================

المواطن لا يجب أن يرى شاشة الموظف.

المواطن يريد:
- معرفة الخدمة.
- تقديم طلب.
- رفع المرفقات.
- متابعة الطلب.
- معرفة النواقص.
- قراءة التعليمات.
- الحصول على مساعدة.

6.1 الصفحة العامة
--------------------------------------------------

المسار:

/services/nosok

المكونات المطلوبة:

العنوان:
خدمات نسك للحج والعمرة

الوصف:

الأزرار:
- تقديم طلب جديد
- متابعة طلب
- عرض المتطلبات

البطاقات:

- استكمال مرفقات

- أيقونة.
- عنوان.
- وصف مختصر.
- حالة إن وجدت.
- زر إجراء.

3. Requirements Preview

تعرض:
- الوثائق المطلوبة.
- شروط الخدمة.
- ملاحظات مهمة.
- روابط التعليمات.

المراحل:

→ مراجعة الطلب
→ استكمال النواقص إن وجدت

- زر متابعة.

6. FAQ Accordion

لا تعرض الأسئلة كقائمة طويلة.

7. Public Help

- مساعد نسك العام.
- دليل الاستخدام.
- تواصل / دعم.

--------------------------------------------------
6.2 صفحة تقديم الطلب
--------------------------------------------------

المسار:

/services/nosok/apply

يجب أن تكون Form Wizard، لا نموذجًا طويلًا مزدحمًا.

الخطوات:

1. اختيار نوع الخدمة:
   - حج
   - عمرة
   - استكمال مرفقات
   - متابعة

2. بيانات مقدم الطلب:
   - الاسم
   - رقم الهوية
   - تاريخ الميلاد
   - رقم الهاتف
   - البريد إن وجد
   - العنوان / المحافظة إن كانت مطلوبة

3. بيانات الطلب:
   - الموسم
   - نوع الخدمة
   - المديرية / الوحدة إن وجدت
   - الملاحظات

4. المرافقون:
   - إضافة مرافق
   - إزالة مرافق
   - بطاقة لكل مرافق
   - حقول أساسية لكل مرافق

5. المرفقات:
   - جواز سفر
   - صورة شخصية
   - إثباتات مطلوبة
   - مرفقات إضافية
   - حالة كل مرفق

6. مراجعة قبل الإرسال:
   - ملخص الطلب
   - ملخص المرفقات
   - تأكيد صحة البيانات
   - تنبيه قانوني أو إداري إن لزم

7. إرسال الطلب:
   - رسالة نجاح
   - رقم طلب
   - رابط متابعة
   - تنبيه لحفظ الرقم المرجعي

قواعد النماذج:
- لا تستخدم placeholder بدل label.
- كل حقل له label واضح.
- helper text عند الحاجة.
- validation باللغة العربية.
- لا تعرض أخطاء backend خام.
- دعم RTL كامل.
- على الموبايل: خطوة واحدة في كل شاشة.
- استخدم Autosave/Draft إن كان موجودًا، وإلا اعرض ذلك كـ planned/disabled.

--------------------------------------------------
6.3 صفحة متابعة الطلب
--------------------------------------------------

المسار:

/services/nosok/track

تحتوي:
- إدخال رقم الطلب.
- إدخال رقم الهوية أو رمز تحقق إن وجد.
- بطاقة حالة الطلب.
- Timeline مبسط بلغة المواطن.
- قائمة النواقص إن وجدت.
- زر رفع مرفق ناقص.
- رابط تواصل أو دعم.

لغة الحالات للمواطن:

submitted        = تم إرسال الطلب
received         = تم استلام الطلب
under_review     = قيد المراجعة
needs_completion = مطلوب استكمال
approved         = تم الاعتماد
rejected         = لم يتم قبول الطلب
assigned         = تم ربط الطلب بحملة / مجموعة
in_followup      = قيد المتابعة
completed        = مكتمل
closed           = مغلق

لا يظهر للمواطن:
- audit الداخلي.
- ملاحظات الموظفين الداخلية.
- أسماء الموظفين إلا إذا السياسة تسمح.
- صلاحيات النظام.
- جداول تشغيلية.
- بيانات طلبات أخرى.
- أي بيانات حساسة غير تخص طلبه.

PostgREST exception / stack trace / raw SQL error

==================================================
9. Role-Based UI
==================================================

يجب فصل الواجهات حسب الدور.

الأدوار:

1. زائر:
   - يرى معلومات عامة ومتطلبات الخدمة.
   - لا يرى الطلبات أو لوحة الموظف.

2. مواطن / مستخدم عام:
   - يرى طلبه فقط.
   - يتابع حالته.
   - يرفع مرفقات.
   - يستكمل نواقصه.

3. موظف نسك:
   - يرى الطلبات المسندة له.
   - يراجع ضمن صلاحياته.
   - لا يرى الإعدادات العليا.

4. مشرف نسك:
   - يرى طلبات نطاقه.
   - يدير فريقه وحملاته.

5. مدير النظام:
   - يرى الإعدادات.
   - يرى التقارير.
   - يدير بعض الصلاحيات.

6. Superuser:
   - يرى كل شيء مع audit.

7. مستخدم مقيد:
   - read-only أو forbidden حسب العقد.

لا تعتمد على إخفاء بصري فقط.
يجب احترام route guards وRBAC الموجودين.

==================================================
10. Anti-Overload UX
==================================================

ممنوع حشر كل شيء في شاشة واحدة.

القواعد:

1. الصفحة الرئيسية تعرض ملخصًا فقط.
2. الجداول الثقيلة في صفحات منفصلة.
3. التفاصيل داخل Drawer أو Detail Page.
4. المرفقات داخل Tabs.
5. Audit قابل للتوسيع.
6. النماذج الطويلة Wizard.
7. الصفحة لا تبدأ بالتفاصيل بل بالقرار/الحالة/الإجراء.
8. لا تزيد الصفحة الرئيسية عن:
   - Hero واحد.
   - Status Strip واحد.
   - 4–6 Metrics.
   - 6–8 Capability Cards.
   - Workflow واحد.
   - Access-Aware Block واحد.
   - Governance Strip صغير.

ترتيب المعلومات:

1. قرار / خطر / مانع.
2. ملخص الحالة.
3. مساحة العمل.
4. التفاصيل والأدلة.

==================================================
11. Responsive Requirements
==================================================

يجب دعم:

- Desktop.
- Laptop.
- Tablet.
- Mobile.

Desktop:
- Sidebar / topbar.
- table + side drawer.
- metrics grid.
- review queue.

Tablet:
- stacked panels.
- reduced columns.
- tabs.

Mobile:
- cards بدل table.
- form wizard.
- bottom sheet.
- sticky primary action.
- no overflow.
- no tiny text.
- no horizontal scroll إلا عند الضرورة وبشكل مضبوط.

تحويلات أساسية:

Data Table:

12. Visual Identity Admin Compatibility
==================================================

يجب ألا تكسر واجهات نسك نظام إدارة الهوية البصرية الموجود.

القواعد:

1. استخدم ThemeData وThemeExtensions المعتمدة.
2. لا hardcode ألوان خارج PWF-SIS.
3. دعم published overrides.
4. دعم dark mode.
5. احترام contrast gate.
6. أي system accent لنسك يكون override محدودًا.
7. لا تجعل نسك يبدو كنظام منفصل بصريًا.
8. لا تنشئ Design System خاصًا بنسك.

نموذج الوراثة:

Platform Default
→ Unit Override
→ System Override
→ Page Context Override
→ Published Runtime Theme

نسك يمكن أن يملك:
- شعار/أيقونة.
- Hero treatment محدود.
- accent محدود.
- صور سياقية.

لكنه لا يملك:
- أزرار مستقلة.
- جداول مستقلة.
- بطاقات مستقلة.
- ألوان مستقلة.
- نظام حالات منفصل.
